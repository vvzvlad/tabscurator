# Avito: как агенту работать

Проверено 18.08.2026 на живом аккаунте: выкачан весь мессенджер (1300+ чатов), прочитаны
переписки, история заказов, остатки в объявлениях, поиск по выдаче. Всё ниже реально
выполнялось, а не выведено из документации.
19.08.2026 инструменты curator обновились (расширение `0.2.162.415`), и часть описанных ниже
граблей закрыта новыми вербами. Главная из них, №2, перепроверена прямо здесь, на живом Авито:
весь мессенджер (ровно 1316 чатов) выкачан из **фоновой** вкладки, без отбора экрана. Остальное
проверялось на Ozon — такие места помечены по месту.

## Коротко

Работает **curator**, инстанс **`main`** (живой залогиненный Brave, execute_js включён).
Внутреннего HTTP API нет — мессенджер живёт на **WebSocket** (`*.rt.avito.ru`), fetch'ем его
не подёргать. Все данные — из DOM по `data-marker`-ам. Главные грабли — **фоновая вкладка**:
в ней не работает бесконечный скролл и душатся таймеры. Из-за этого легко получить
уверенно-неверный ответ («в аккаунте всего 12 чатов», реально 1316). С 19.08.2026 это лечится
без отбора экрана — `set_focus_emulation` плюс `scroll_until` (№2).

И обязательное правило: фотографии объявления смотреть до любых выводов о товаре — сразу
следующий раздел.

## Смотреть, а не только читать: фотографии обязательны

**Фотографии объявления смотреть глазами до любых выводов о товаре.** Не «собрал ссылки на
картинки», а именно посмотрел.

Само правило выведено не здесь, а на Ozon (см. `ozon.md`, там же и конкретные случаи, когда
характеристики и заголовок не содержали того, что нарисовано на фото); на Авито 19.08.2026
измерялась только лента чатов, так что **прямых авитовских подтверждений у правила нет**.
Косвенное указание в ту же сторону — плитки заказов: названия товаров лежат там **только** в
`img[alt]`, в тексте их нет. То есть картинка бывает единственным носителем данных и на Авито —
хотя конкретно `alt` читается атрибутом из DOM, смотреть для этого не надо.

Остальное — ожидание по природе площадки, а не замер: текст объявлений часто скупой, а состояние
товара, комплектность, реальная модель и дефекты видны на фотографиях, в описании их может не
быть вовсе.

Тот же принцип шире: когда страница или список не читаются целиком программно, скриншот и глаза
человека — законный источник правды, а не признак поражения. На Ozon полный перечень позиций
корзины удалось получить только так, ни API, ни DOM его не отдали (см. `ozon.md`).

## Инстансы и антибот

- **`main`** — работает: живые куки, `execute_js` разрешён.
- **`work`** — Авито отдал IP-капчу («Доступ ограничен: проблема с IP») на первый же заход.
  Не использовать.
- **`infra`** — `execute_js` выключен в опциях расширения.
- `chrome-devtools-mcp` не проверялся; по опыту Ozon (см. `ozon.md`) шансов мало.

## Почему данные только из DOM

Мессенджер ходит по WebSocket. В `performance.getEntriesByType('resource')` из полезного —
только счётчики `stat/radar` и служебные `/web/1/*` (бейджи уведомлений). REST-эндпоинтов
уровня «отдай список чатов JSON'ом» не видно. Поэтому: скроллить живой DOM и разбирать маркеры.

## Грабли

### №1: спящие вкладки — «Cannot access contents of the page»

Вкладка, выгруженная браузером из памяти (discarded), отвечает на `get_text`/`execute_js`
ошибкой `Cannot access contents of the page. Extension manifest must request permission…`.
Это не про пермишены — вкладку надо разбудить: `navigate_tab` на её же URL (перезагрузка),
дальше всё работает.

С 19.08.2026 у этого случая есть отдельный код ошибки `tab_discarded` вместо невнятного текста
про манифест, и своя верба `wake_tab(instance, tab_id)`, которая вкладку будит. Она **всегда
перезагружает** страницу: на живой вкладке это полная потеря состояния, а не no-op, — звать
только в ответ на `tab_discarded`. Старый приём с `navigate_tab` остаётся рабочим и удобнее,
когда вкладку всё равно надо куда-то увести. Проверено на Ozon, на Авито не перепроверялось.

### №2: фоновая вкладка не листается — снято эмуляцией фокуса

Замерено: в неактивной вкладке подгрузка списка чатов молча стоит — список замирает на первой
порции, и это выглядит как «конец истории». Скролл-контейнера у списка нет, скроллится само окно
(`window.scrollTo(0, document.body.scrollHeight)`), но само по себе это ничего не даёт.
Объяснение по поведению (отдельно не измерялось): бесконечный скролл держится на
`IntersectionObserver`, которому нужна растеризуемая вкладка. Раньше отсюда был один выход —
`focus_tab` или вкладка, которую пользователь сам держит активной, то есть отбор экрана.

**19.08.2026 проверено на живом Авито: экран отбирать больше не нужно.** Пара
`set_focus_emulation` + `scroll_until` выкачивает весь мессенджер из фоновой вкладки.

Замер в фоновой вкладке `/profile/messenger` (`active: false`). Состояние до эмуляции:

```
{"vis": "hidden", "focus": false, "ch": 10}
```

`scroll_until(count_selector='[data-marker="channels/channel"]', stable_rounds=5,
interval_ms=900, focus=false)` → `{count: 10, rounds: 6, stopped: "stable", elapsed_ms: 4557}` —
не сдвинулось ни на единицу. Затем `set_focus_emulation(enabled=true)` →
`{ok: true, enabled: true}`, и сразу, без каких-либо других действий:

```
{"vis": "visible", "focus": true, "ch": 39}
```

То есть верба переключает **и** `document.hasFocus()`, **и** `document.visibilityState`: лента
начала грузиться сама, счётчик вырос с 10 до 39 ещё до прокрутки. Дальше `scroll_until(focus=false)`
в той же фоновой вкладке:

| прогон | count | rounds | stopped | elapsed_ms |
|---|---|---|---|---|
| 1 | 837 | 34 | deadline | 30 663 |
| 2 | 1195 | 24 | deadline | 30 362 |
| 3 | 1312 | 15 | deadline | 30 506 |
| 4 | 1316 | 11 | stable | 9 255 |

Итог: 10 → 1316 чатов, лента исчерпана (`stopped: "stable"`), экран у человека не отбирался ни
разу. Прежняя оценка «1300+ чатов» — это ровно 1316.

Три `deadline` подряд ровно на ~30 с — то самое молчаливое зажатие `timeout_ms` (№10): окно
всегда 30 секунд, сколько ни проси, поэтому `scroll_until` надо звать циклом, пока не придёт
`stable`. По завершении —
`set_focus_emulation(enabled=false)`, чтобы отцепить дебаггер: пока эмуляция включена, висит
полоса «идёт отладка», а присоединённый `chrome.debugger` детектируем антиботом (на этих прогонах
Авито не отреагировал, но на Ozon риск реален).

Сама `scroll_until(count_selector, container_selector?, direction?, stable_rounds?, interval_ms?,
target_count?, focus?, timeout_ms?)` → `{ok, count, rounds, stopped, elapsed_ms}` крутит цикл в
воркере расширения (свежая инъекция каждые `interval_ms`), поэтому троттлинг таймеров фоновой
вкладки ей не помеха; галочка `execute_js` для неё не нужна. На Ozon она в фоне и без эмуляции
подняла список покупок с 17 ссылок до 601 за 9949 мс — там лента не требует видимости.

Чего эмуляция **не** лечит: остаток за свёрнутым блоком или кнопкой «показать ещё» — там ни
видимость, ни `focus: true` ни при чём, надо кликать (пример — корзина Ozon, см. `ozon.md`).

И предупреждение: `stopped: "stable"` приходит и когда лента реально кончилась, и когда она не
сдвинулась ни на позицию, — ответ в обоих случаях бодрый `ok: true`, отличаются только числа.
В замере выше первый прогон дал ровно это: `10 → 10, stable`. Счётчик надо мерить самому **до**
вызова и сравнивать, иначе неполный результат уедет в выводы как полный.

### №3: таймеры в фоне душатся — команды «умирают», но работают

В фоновой вкладке `setTimeout` троттлится, цикл со `sleep(700)` растягивается, `execute_js`
отваливается по `timeout` — а код при этом **продолжает выполняться** и состояние копится.
Длинные циклы синхронно гонять нельзя.

Раньше это лечилось самодельным fire-and-forget раннером (`window.__runnerActive` плюс опрос
глобала). С 19.08.2026 для того же есть штатная пара верб — проверена на Ozon, на Авито не
перепроверялась:

- `start_js(instance, tab_id, code, world?)` → `{ok, job_id}` немедленно. Код выполняется в
  странице как awaited async body, поэтому top-level `await` и `return` в нём работают;
- `poll_job(instance, tab_id, job_id, max_bytes?)` → `{ok, state, value?, message?}`, где
  `state` ∈ `running` | `done` | `error` | `unknown`, а `max_bytes` по умолчанию 40000 —
  резать ответ вручную больше не надо.

Ловушка: **`unknown` — это не «ещё работает»**. Это «состояния в странице больше нет»: вкладку
перезагрузили, выгрузили или закрыли, либо job_id не тот. Спутать `unknown` с `running` — значит
вечно ждать результат, которого уже не будет. Ещё две мелочи: записи о job'ах копятся в
`window.__curatorJobs` до навигации (`poll_job` их не съедает), поэтому долгоживущую вкладку с
сотнями job'ов надо переоткрывать; а job, запущенный с `world: "ISOLATED"`, и опрашивать надо с
тем же `world`, иначе снова `unknown`.

### №4: multi-statement код обязан делать `return`

С `await_promise: true` многострочный сниппет без явного `return` отвечает `value: null` —
молча. Однострочное выражение работает и без return. Top-level `await`/`return` требуют
`await_promise: true`. Правило в силе: перепроверено 19.08.2026 (на Ozon) — ничего не изменилось.

### №5: поиск мессенджера врёт

Поле поиска (`searchInput/input`, оно же `?q=` в URL `/profile/messenger`) выглядит
серверным, но чатов, не подгруженных в ленту, **не находит**: на аккаунте лежали десятки
чатов со словом «сервер» в заголовке объявления — поиск ответил «Ничего не нашлось».
«Не нашлось» ≠ «нет». Единственный надёжный путь — выкачать весь список скроллом и
фильтровать самому.

### №6: даты в списке чатов — без года

Превью чата показывает «14 апр.» и не говорит какого года: лента за несколько лет выглядит
одинаково. Год есть только внутри чата, в разделителях («24 декабря 2024 г.»). По
превью-датам нельзя ни сортировать, ни датировать.

### №7: история чата открывается обрезанной

Канал грузит только хвост (последние ~15–20 сообщений), причём хвост может начинаться с
середины разговора — выглядит как цельная переписка и провоцирует неверные выводы
(проверено на себе: «купил 1 сервер» вместо реальных 3+1, потому что июльская часть чата
не подгрузилась). Старшие сообщения докручиваются `scrollTop = 0` по скролл-контейнеру в
цикле, критерий — рост числа `[data-marker="message"]`; в фоновой вкладке докрутка стоит по той
же причине, что и лента чатов (№2). Значит и лечиться должна так же — `set_focus_emulation`
вместо отбора экрана; именно на докрутке истории это не перепроверялось, но природа одна.

### №8: вкладки живут своей жизнью

Посреди работы прилетает `no_such_tab` — пользователь закрыл вкладку, и всё состояние в
`window.__*` пропало. Свою вкладку открывать через `open_tab` и не привязываться к чужим.

Механизм разобран 19.08.2026 (на Ozon, но он общий — это поведение самого curator, не магазина):
лизинг от `open_tab(lease_ttl_s=…)` защищает **адрес**, а не вкладку. Стоит увести её
`navigate_tab`'ом на другой url — и строка исключения перестаёт совпадать с живым адресом,
вкладка становится незащищённой, а очередной проход куратора её убирает. Умирает не сразу:
сначала всё работает как ни в чём не бывало, потом любая верба отвечает `no_such_tab`. То же
делает любой редирект, которого ты не просил. Лечение: не уходить с адреса лизинга либо после
каждой навигации перечитывать живой url и перевыписывать защиту через `set_exemption`. И помнить,
что `no_such_tab` сегодня одинаково значит «такого id не было», «человек закрыл вкладку» и
«прибрал куратор» — различить нельзя
([#72](https://gitea.vvzvlad.xyz/projects/tabscurator/issues/72)).

Заодно у всех верб появился необязательный `expected_session` — страховка от работы не с той
сессией браузера; `session_id` берётся из `list_instances` / `list_tabs`.

### №9: поиск объявлений по партномеру подсовывает мусор

`/all?q=HMAA8GL7AMR4N` → Авито молча решает, что запрос бессмысленный, и отдаёт
«рекомендации»: KVM-переключатели вместо серверной памяти, без какого-либо признака
подмены. Запросы формулировать по-человечески («память 64gb ddr4 ecc reg»), выдачу
фильтровать регекспом на клиенте.

### №10: `timeout_ms` молча зажимается до 30 секунд

Проверено на Ozon 19.08.2026 (верба общая, к магазину отношения не имеет):
`navigate_tab(wait_until='selector', …, timeout_ms=45000)` вернул
`{ok: true, matched: false, elapsed_ms: 30006}`. Потолок `EXECUTE_JS_MAX_TIMEOUT_MS` — 30 000 мс,
всё, что больше, зажимается без единого слова в ответе; касается всех верб с `timeout_ms`
([#71](https://gitea.vvzvlad.xyz/projects/tabscurator/issues/71)).

Живая иллюстрация — выкачка ленты чатов из №2: три вызова `scroll_until` подряд закрылись по
`deadline` ровно на ~30 с (30 663 / 30 362 / 30 506 мс), и только четвёртый дошёл до
`stopped: "stable"` за 9 255 мс — суммарно ~101 с работы, разложенных на четыре вызова. Окно
всегда 30 секунд, сколько ни проси, поэтому длинные вербы надо звать циклом до содержательного
признака конца.

Бьёт и по рецепту «Прочитать чат целиком» ниже: там `navigate_tab` с
`wait_until: 'selector'`, и `matched: false` в нём может означать не «страница не загрузилась»,
а «ждали 30 секунд, сколько бы ни запросили». Вообще `matched: false` — это всегда про условие, а не
про загрузку: на Ozon такой ответ пришёл на полностью отрисованной странице просто из-за
неверного селектора. Значит при `matched: false` проверять сперва селектор, потом время — и в
любом случае убедиться в загрузке отдельно, `get_text`'ом.

## data-marker'ы

| где | маркер | что |
|---|---|---|
| список чатов | `channels/list`, `channels/channel` | контейнер и элемент чата |
| | `channels/user-title`, `channels/item-title`, `channels/item-price` | собеседник, объявление, цена |
| | `channels/last-message`, `channels/channel-datetime` | превью и дата (без года!) |
| | `searchInput/input` | поиск (не доверять, №5) |
| внутри чата | `messagesHistory`, `messagesHistory/list`, `message`, `messageText` | история и сообщения |
| | `icon/messenger-statusRead` | галочка прочтения — как признак «своего» сообщения НЕ работает (пометила все 122) |
| поиск объявлений | `[data-marker="item"]` + `[itemprop="name"]`, `[itemprop="price"]` | карточка выдачи, 50 шт/страница |

Свои/чужие сообщения надёжнее различать по содержимому: блоки-цитаты в переписке содержат
имя автора цитируемого сообщения.

## Рецепты

### Выкачать список чатов целиком

Видимая вкладка больше не нужна — всё делается в фоне (№2):

1. `open_tab(url='https://www.avito.ru/profile/messenger', active=false, lease_ttl_s=1800)`;
2. `set_focus_emulation(enabled=true)` — вкладка становится «видимой», лента начинает грузиться
   сама;
3. `scroll_until(count_selector='[data-marker="channels/channel"]', stable_rounds=5,
   interval_ms=900, focus=false)` **циклом**, пока не придёт `stopped: "stable"`: из-за зажатия
   таймаута (№10) вызовы упираются в окно ~30 с и закрываются по `deadline`, пока лента не
   кончится; на 1316 чатов ушло четыре вызова — три по ~30 с и последний на 9 с, суммарно ~101 с;
4. собрать данные коллектором (ниже) одним `execute_js` с `await_promise: true` — сниппет делает
   top-level `return`, без флага придёт `null` (№4);
5. `set_focus_emulation(enabled=false)` — отцепить дебаггер.

Коллектор — словарь по `href` (ссылка канала уникальна): гарантирует, что повторно попавшиеся в
DOM элементы не задвоятся.

```js
const get = (el, m) => { const n = el.querySelector(`[data-marker="${m}"]`); return n ? n.textContent.trim() : ''; };
window.__avitoChats = window.__avitoChats || {};
const collect = () => document.querySelectorAll('[data-marker="channels/channel"]').forEach(el => {
  const a = el.closest('a[href]') || el.querySelector('a[href]');
  const href = a ? a.getAttribute('href') : 'x' + Math.random().toString(36).slice(2);
  window.__avitoChats[href] = { user: get(el,'channels/user-title'), item: get(el,'channels/item-title'),
    price: get(el,'channels/item-price'), msg: get(el,'channels/last-message').slice(0,100),
    date: get(el,'channels/channel-datetime'), href };
});
collect();
return Object.keys(window.__avitoChats).length;
```

`window.__avitoChats` живёт до навигации, поэтому при повторном запуске в той же вкладке словарь
надо обнулять (`window.__avitoChats = {}`): иначе возвращаемое число накопительное, и сверить его
с `count` от `scroll_until` нельзя. Элементы без `href` кладутся по случайному ключу, так что
каждый лишний проход ещё и плодит для них дубли.

Самодельный раннер со `scrollTo` и `sleep` больше не нужен — прокрутку целиком делает
`scroll_until`, коллектор вызывается один раз в конце. Конец истории виден по футеру сразу после
последнего чата и отсутствию спиннера. Сохранять `msg` сразу — превью позволяет фильтровать чаты
с мёртвыми объявлениями («Объявление временно недоступно»), у которых `item` пуст.

### Прочитать чат целиком

URL `/profile/messenger/channel/<id>` (id из `href` в списке). `navigate_tab` с
`wait_until: 'selector'`, `selector: '[data-marker="message"]'`. Затем докрутка вверх:

```js
const scrollers = [...document.querySelectorAll('div')]
  .filter(d => d.scrollHeight > d.clientHeight + 20 && d.querySelector('[data-marker="message"]'));
const sc = scrollers[scrollers.length - 1];         // самый внутренний со скроллом
// цикл: sc.scrollTop = 0; sleep(500); пока растёт число [data-marker="message"]
```

Текст истории целиком — `innerText` контейнера `messagesHistory`: даты-разделители с годом
и сообщения идут по порядку. Ссылки на объявление и профиль продавца — `a[href*="/user/"]`
в шапке чата (там же item id: `?id=<NNNNNNNNNN>`).

### Поиск по объявлениям

`https://www.avito.ru/all?q=<запрос>` или `/moskva?q=...` (регион в пути). Разбор:

```js
[...document.querySelectorAll('[data-marker="item"]')].map(el => ({
  title: el.querySelector('[itemprop="name"]')?.textContent.trim(),
  price: el.querySelector('[itemprop="price"], [data-marker="item-price"]')?.textContent.trim()
}))
```

Помнить про №9: выдача может оказаться «рекомендациями», проверять релевантность.

## Что НЕ работает (проверено, не тратить время)

- Поиск мессенджера по тексту/названию для незагруженных чатов (№5).
- `performance`-эндпоинты как замена DOM: мессенджер — WebSocket, HTTP API нет.
- Галочка `statusRead` как детектор своих сообщений (пометила вообще все).
- Партномер в поиске объявлений (№9).
- Глубина истории: чаты старше ~3 лет Авито не отдаёт вовсе (по неофициальным данным
  скрывает; лента просто заканчивается).

## Безопасность

- Всё происходит в **настоящем браузере пользователя под его логином**. Отправка сообщения
  в чат — от его имени; черновики показывать, отправлять только по явной команде.
- Открытие чата гасит счётчик «непрочитанных» — это видимый след, как и любые клики.
- Чтение (DOM, innerText) безопасно и обратимо. Всё, что меняет состояние — сообщения,
  редактирование объявлений, заказы — только по явному указанию; см. правило про
  деструктивные операции в `AGENTS.md`.
- В контекст и транскрипт утекают персональные данные из переписок: телефоны, адреса,
  суммы, номера карт продавцов. Не тащить лишнего.
